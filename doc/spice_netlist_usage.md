# Exporting a SPICE Netlist and Simulating

This document explains how to export a circuit described with cuprite_wire as a SPICE netlist and
simulate it with ngspice from Rust. See `doc/circuits.md` for describing circuits (parts, labels,
subcircuits, errors) and `doc/dev/spice_netlist_format.md` for the SPICE format.
A complete example is in `examples/spice_rc_filter.rs` (`cargo run --example spice_rc_filter`);
`examples/sensor_frontend/` tests each subcircuit of a board with a test bench.

## 1. Pipeline

```rust
let netlist = bench               // CircuitBuilder: the test bench (section 3)
    .build(&options)
    .to_netlist()?                // Netlist: the same as for KiCad
    .to_spice()?                  // SpiceNetlist: SPICE information resolved and checked
    .with_title("rc_filter");     // optional title line (default: "cuprite_wire")
let out = netlist.node("/OUT").unwrap().to_string();   // SPICE node name of a net
let simulation = netlist
    .deck()                       // SpiceDeck: the netlist with analyses
    .directive(".options reltol=1e-4")
    .control(["ac dec 20 1 100k".to_string(), format!(r#"meas ac f3db WHEN vdb("{out}")=-3"#)])
    .run()?;                      // runs ngspice (section 5)
let f3db = simulation.value("f3db");   // Option<f64>; `expect_value` panics with the log instead
```

- `to_spice()` returns `Err(CircuitErrors)` with all errors found (section 4).
- The output is deterministic. `SpiceNetlist` and `SpiceDeck` implement `Display`;
  `SpiceNetlist::write` writes the netlist alone (section 6).

## 2. Defining parts

`Part::spice()` returns `Option<SpicePartInfo>`; `None` (the default) means that the part cannot be
simulated, and exporting a circuit containing it fails with `SpiceUnsupported`.
Parts generated by `kicad_part!` derive it from the symbol's `Sim.*` fields or a `sim` block
(`doc/kicad_part_macro.md` section 4); `spice_part!` makes a part from a model alone
(`doc/spice_part_macro.md`).

```rust
fn spice(&self) -> Option<SpicePartInfo> {
    // Resistor: R<ref> <pin 1> <pin 2> 10k
    Some(SpicePartInfo::element(SpiceElement::new('R', ["1", "2"], "10k")))
}

fn spice(&self) -> Option<SpicePartInfo> {
    // Op-amp with a subcircuit model: XU1 <in_p> <in_n> <vdd> <vss> <out> AD8051
    let element = SpiceElement::new('X', ["in_p", "in_n", "vdd", "vss", "out"], "AD8051")
        .with_model(ModelSource::include(concat!(env!("CARGO_MANIFEST_DIR"), "/models/ad8051.lib")));
    Some(SpicePartInfo::element(element).with_unused_pins(["nc"]))
}

fn spice(&self) -> Option<SpicePartInfo> {
    // A connector: not simulated, but its pins still name the nets.
    Some(SpicePartInfo::Excluded)
}
```

- `SpiceElement::new(device, nodes, args)` is the counterpart of KiCad's `Sim.*` fields:
  - `device`: the SPICE device letter (`R C L V I D Q M J X B E F G H ...`), which selects the
    element type and must match the model, whatever the reference prefix is.
  - `nodes`: pin IDs of the part **in the order of the model's nodes** (`Sim.Pins`).
  - `args`: everything after the nodes: value, model or subcircuit name, parameters.
    `;` and `$` (comments) and line breaks are rejected, so values like `100uF;16V` are caught.
  - `with_model`: `ModelSource::include(path)` for a model library (`.include`, absolute paths only,
    since ngspice resolves relative paths against its working directory), or
    `ModelSource::inline(name, text)` for a `.model`/`.subckt` written into the deck. Inline models
    are deduplicated by name (case-insensitively); different definitions with one name are an error.
    Models written for PSpice or LTspice are marked with `.pspice()` / `.ltspice()`
    (`ModelSource::include(path).pspice()`), so that ngspice reads them in its compatibility
    mode (section 5).
- **Every pin must be used**: by an element, or connected inside the part (`internal_connections()`)
  to a pin that is. Pins intentionally left out of the model are listed with `with_unused_pins`;
  others are reported as `SpicePinUnmapped`, which catches mistakes in the pin mapping.
- A part may have **several elements** (`SpicePartInfo::elements`), e.g. the units of a dual op-amp.
  Each gets a distinct suffix (`with_suffix("A")` -> `XU1A`). Use a `.subckt` for a model with
  internal nodes.
- `SpicePartInfo::check` checks the information against the part's pins (`PartPins::of(&part)`)
  without building a circuit.

## 3. Test benches and simulation-only parts

Analyses and stimuli belong to the test, not to the circuit:

- Put the circuit under test in a **test bench circuit** as a subcircuit (or build it directly in
  the bench), and add simulation-only parts from `cuprite_wire::spice`:
  - `IndependentSource::voltage(dc)` / `IndependentSource::current(dc)` with pins `p` and `n`
    (`IndependentSource::P` / `IndependentSource::N`),
    `.with_ac(magnitude)` and `.with_waveform(Waveform::sin(..) | Waveform::Pulse { .. } | Waveform::Pwl(..))`.
  - `Ammeter`: a 0 V source (`VM1`, ...) whose current from `p` to `n` (`Ammeter::P` / `Ammeter::N`)
    is the vector `i(VM1)`.
  - Digital stimuli in `cuprite_wire::spice::digital` (see below), and drivers and receivers of
    IBIS models in `cuprite_wire::spice::ibis` (feature `ibis`, see below).

  These parts have no KiCad information, so the bench cannot be exported to KiCad; the circuit
  under test still can.
- Add analyses to a `SpiceDeck`: `directive(...)` for dot lines (`.options`, `.ic`, `.tran`) and
  `control([...])` for ngspice front-end commands. The `.control` block starts with
  `set filetype=ascii`, `set wr_singlescale` and `set wr_vecnames` and ends with `quit`.

### Digital stimuli

`cuprite_wire::spice::digital` drives a circuit with logic levels through the electrical model
of a pin, for open-loop tests of the digital inputs of a circuit (UART, PWM, open-drain lines):

```rust
use cuprite_wire::spice::digital::*;

let tx = DigitalSequence::new(Level::High).uart(10e-6, 115_200.0, b"Hi");
let driver = bench.instantiate_part(DigitalDriver::new(OutputCharacteristics::cmos(3.3), tx));
let input = InputCharacteristics::cmos(3.3).with_pull(Pull::up(3.3, 10e3));
let load = bench.instantiate_part(DigitalLoad::new(input.clone()));
// ... connect `driver[DigitalDriver::OUT]` / `load[DigitalLoad::IN]`, run a transient analysis ...
let read = input.decode(table.scale(), table.column(r#"v("/RX")"#).unwrap());
```

- `DigitalSequence`: an initial `Level` (`Low`, `High`, `HiZ`) and the times it changes
  (`.at(time, level)`, non-decreasing times). `.uart(start, baud, bytes)` appends 8N1 frames,
  `.pwm(start, period, duty, cycles)` a PWM signal. `level_at(time)` reads it back.
- `OutputCharacteristics`: `low` / `high` voltages (`V_OL` / `V_OH`), output `resistance`,
  `rise_time` / `fall_time`. Edges are linear over the whole swing (0-100 %, 1.25 times a
  10-90 % datasheet value); an edge cut short by the next change starts from where it was.
  Resistance and edge times must be positive: ideal steps make the simulation fail to converge.
  `cmos(vdd)` gives placeholder values (50 ohm, 2 ns); take the real ones from the datasheet.
- `DigitalDriver::new(output, sequence)` (pins `out`, `gnd`; `XDRV1`) is written as a subcircuit
  of its own, `cuprite_digital_<hash>`: a PWL source (`VD_out`) behind the output resistance
  (`RO_out`). If the sequence has `HiZ`, a switch (`SO_out`, controlled by the PWL `VE_out`)
  replaces the resistor and opens
  to `HIZ_RESISTANCE` (1 Gohm); the source holds its last level meanwhile, so the edge from `HiZ`
  is set by the output resistance and the load. `sequence.voltage_waveform(&output)` gives the
  PWL alone, for an `IndependentSource`.
- `InputCharacteristics`: thresholds `threshold_low` / `threshold_high` (`V_IL` / `V_IH`, with
  hysteresis between them), `capacitance`, `pull` (`Pull::up(voltage, resistance)` /
  `Pull::down(resistance)`) and `leakage` (current into the pin). `DigitalLoad::new(input)`
  (pins `in`, `gnd`) writes the capacitor (`CDL1C`) and the pull resistor and leakage as their
  Norton equivalent (`RDL1P` to `gnd`, current source `IDL1I` into `in`); without any of them it
  is left out of the simulation.
- `input.read(voltage, previous)` gives the level an input reads; `input.decode(time, voltage)`
  turns the samples of a transient analysis into a `DigitalSequence`, with the times of the
  changes interpolated at the thresholds.

### IBIS buffers

With the feature `ibis`, `cuprite_wire::spice::ibis` simulates the I/O buffers of a device from its
IBIS model (`.ibs`) instead of `OutputCharacteristics` / `InputCharacteristics`: the I-V tables of
the driver and the clamps, the edges of `[Rising Waveform]` / `[Falling Waveform]` (or `[Ramp]`),
`C_comp` and the package parasitics of the pin. The file is read with `cuprite_wire::ibis` (the crate `cuprite_wire_ibis`).

```rust
use cuprite_wire::{
    ibis::Corner,
    spice::{digital::*, ibis::*},
};

let ibs = cuprite_wire::ibis::parse(&std::fs::read_to_string("mcu.ibs")?)?;
let tx = IbisBuffer::of_pin(&ibs, "MCU", "12", Corner::Typ)?;
let rx = IbisBuffer::of_pin(&ibs, "MCU", "13", Corner::Typ)?;
let seq = DigitalSequence::new(Level::High).uart(1e-6, 1e6, b"Hi");
let driver = bench.instantiate_part(IbisDriver::new(tx, seq));
let receiver = bench.instantiate_part(IbisReceiver::new(rx.clone()));
// ... connect `driver[IbisDriver::OUT]` / `receiver[IbisReceiver::IN]`, run a transient analysis ...
let read = rx.input().unwrap().decode(table.scale(), table.column(r#"v("/RX")"#).unwrap());
```

- `IbisBuffer::of_pin(&file, component, pin, corner)` takes the `[Model]` of a pin of a
  `[Component]` with the parasitics of the pin (`R_pin` / `L_pin` / `C_pin`, or else `R_pkg` /
  `L_pkg` / `C_pkg`); `IbisBuffer::new(&model, &parasitics, corner)` takes any model. For a pin
  naming a `[Model Selector]`, `of_pin` takes its default (first) model and
  `IbisBuffer::of_pin_model(&file, component, pin, model, corner)` one of the others
  (`file.model_selector(name)` lists them with their descriptions). `Corner::Typ` / `Min` / `Max`
  select the column of the values (a value that is `NA` falls back to typical; in a table, a column
  takes the rows that have values, and the typical column if it has none). The supported model
  types are `Input`, `Output`, `I/O`, `3-state`, the open drain, sink and source types, their ECL
  versions (`Input_ECL`, `Output_ECL`, ...; `[Pulldown]` is relative to the supply, as the
  specification defines), `Terminator`, and `Series` (see below).
- The sequence is the level of the pin (the pad), not of the logic inside the device: `Polarity`
  (`Inverting`) and `Enable` (`Active-Low`) of the model are not applied.
- `IbisDriver::new(buffer, sequence)` (pins `out`, `gnd`; `XDRV1`) plays a `DigitalSequence`. The
  model's `[Pullup]` and `[Pulldown]` are weighted by two PWL sources that follow the edges of the
  model (`buffer.edges()`): the weights that reproduce its `[Rising Waveform]` /
  `[Falling Waveform]` in their test fixtures, delay included, as in the IBIS specification and
  KiCad (two waveforms with different `V_fixture` give both weights; one gives them with
  `ku + kd = 1`). An edge without waveforms switches linearly over the time of `[Ramp]` (its
  20-80 % time divided by 0.6, as KiCad does). Waveforms with a fixture other than `R_fixture`,
  `V_fixture` and `C_fixture` (`L_fixture`, `R_dut`, `L_dut`, `C_dut` other than 0) are not used
  and listed in `buffer.notes()`. `HiZ` turns both weights off. A level the model cannot drive
  (`HiZ` on an `Output`, `High` on an open drain) panics.
- `IbisReceiver::new(buffer)` (pins `in`, `gnd`; `XRX1`) is the package, `C_comp` and the clamps;
  an I/O model is its receiver with the driver off. A `Terminator` model is a receiver with its
  `[Rgnd]`, `[Rpower]` and `[Rac]` + `[Cac]`.
- `buffer.input()` gives `InputCharacteristics` with the model's `Vinl` / `Vinh` (those of
  `[Model Spec]` at the corner if given) as the thresholds, to `decode` the voltage of the pin
  (`None` if the model lacks them).
- Both are subcircuits named after a hash of their definition (`cuprite_ibis_model_<hash>` for the
  model, `cuprite_ibis_<hash>` for the driver); the I-V tables are XSPICE `pwl` code models, which
  the usual builds of ngspice load. Beyond the voltages of a table, its end segments are extended.
- Not used: `Series_switch` models, `[Series Current]` / `[Series MOSFET]`, the `*_diff` model
  types (which need `[External Model]`), `[Package Model]`, `[Receiver Thresholds]` and
  `[Submodel]`.

Differential pairs (`[Diff Pin]`):

```rust
let tx = IbisDiffBuffer::of_pin(&ibs, "PHY", "A5", Corner::Typ)?; // either pin of the pair
let rx = IbisDiffBuffer::of_pin(&ibs, "FPGA", "B7", Corner::Typ)?;
let driver = bench.instantiate_part(IbisDiffDriver::new(tx, seq));
let receiver = bench.instantiate_part(IbisDiffReceiver::new(rx.clone()));
// ... connect `p` to `p` and `n` to `n` (through a differential line), run a transient analysis ...
let vdiff = rx.vdiff().unwrap(); // high above +vdiff, low below -vdiff
```

- `IbisDiffBuffer::of_pin(&file, component, pin, corner)` takes the row of `[Diff Pin]` with the
  pin: the buffers of its non-inverting and inverting pins (`p()`, `n()`, each with its own model
  and parasitics, as `IbisBuffer::of_pin`), `vdiff()` and `tdelay()` at the corner (0 when `NA`).
  `of_pin_model` chooses the model of a `[Model Selector]` for both pins;
  `IbisDiffBuffer::new(p, n, vdiff, tdelay)` pairs any two buffers.
- `IbisDiffDriver::new(buffer, sequence)` (pins `p`, `n`, `gnd`; `XDRV1`) plays the sequence on
  `p` and its complement on `n`, `tdelay` later (`HiZ` releases both). A pin whose model cannot
  drive high (open drain, as in TMDS) or low (open source) is released instead.
- `IbisDiffReceiver::new(buffer)` (pins `p`, `n`, `gnd`; `XRX1`) puts the receiver of each buffer
  on its pin. `cuprite_wire` does not decode the difference: compare `v(p) - v(n)` with
  `vdiff()`.
- A `Series` model that `[Series Pin Mapping]` puts between the two pins of the pair, such as an
  on-die 100 ohm termination, is part of both the driver and the receiver (`termination()`;
  `with_termination` adds one to a pair made with `new`). It connects the pins outside their
  packages. `IbisSeries::of_pins(&file, component, pin1, pin2, corner)` / `IbisSeries::new(&model,
  corner)` (pins `a`, `b`; `XSER1`) is such a model as a part of its own: `[R Series]`,
  `[L Series]` with `[Rl Series]`, and `[C Series]` with `[Lc Series]` and `[Rc Series]`, in
  parallel.

Which to use:

| | `spice::digital` | `spice::ibis` | co-simulation (`doc/cosimulation.md`) |
|---|---|---|---|
| Pin model | linear: levels, resistance, edges from a datasheet | the device's IBIS model: nonlinear driver, clamps, package | `OutputCharacteristics` / `InputCharacteristics`, as `spice::digital` |
| Stimulus | a `DigitalSequence` fixed before the run | a `DigitalSequence` fixed before the run | a Rust model reacting to the circuit while it runs |
| Use for | logic-level tests of a circuit's inputs | signal integrity: ringing, overshoot, clamping, edges into a real load | closed-loop tests with firmware |
| Needs | ngspice | ngspice with XSPICE; feature `ibis` | the ngspice shared library; feature `shared-ngspice` |

## 4. Node names and ground

SPICE node names are the net names of the netlist (`doc/circuits.md` section 5),
converted as KiCad does, so that the deck can be compared with KiCad's own export:

| Net | Node |
|---|---|
| `/OUT`, `/stage1/OUT`, `/RcStage#1/OUT` | unchanged |
| `/amp/I{slash}O` | `/amp/I/O` (escapes undone) |
| `Net-(R1-Pad2)`, `unconnected-(U1-NC-Pad7)`, `/a(b) c` | `Net-_R1-Pad2_`, `unconnected-_U1-NC-Pad7_`, `/a_b__c` (`% ( ) , [ ] < > ~` and whitespace -> `_`) |
| `GND` (any case), `0` | `0` (the ground) |

`SpiceNetlist::node(net_name)` returns the node name. In front-end commands quote names containing
`/` or `-`: `v("/OUT")`.

Besides the errors of `to_netlist` (`doc/circuits.md` section 6), `to_spice` reports (each with the
trace of the part or the label):

| Error (`CircuitErrorKind`) | Cause |
|---|---|
| `SpiceUnsupported` | `spice()` returns `None` |
| `InvalidSpiceElement` | invalid device letter, suffix or arguments, relative include path, empty model, no elements, duplicate suffixes |
| `UnknownPinId` | an element or `unused_pins` refers to a pin the part does not have |
| `SpicePinUnmapped` | a pin is not used by the model (section 2) |
| `InvalidSpiceNodeName` | a node name ngspice cannot read: non-ASCII characters (ngspice replaces them, which can merge nets), `= { } ' " ;`, or a leading `$` |
| `SpiceNodeCollision` | two nets give the same node name ignoring case (ngspice would merge them silently), e.g. `/A` and `/a`, or `GND` and `0` |
| `SpiceElementCollision` | two element names differ only in case |
| `SpiceModelConflict` | two parts define an inline model with the same name differently |
| `GroundMissing` | no net named `GND` or `0` is used by an element |

## 5. Running ngspice

`SpiceDeck::run()` writes the deck to a new directory under the system temporary directory
(`$TMPDIR`), runs ngspice there and returns a `Simulation`:

- `table("ac.txt")` reads a `wrdata` file: `names()`, `scale()`, `column(name)` and
  `interpolate(name, x)`. Column names are matched case-insensitively and ignoring double quotes
  (ngspice writes `v("/OUT")` as `v(/OUT)` but keeps the quotes of `vdb("/OUT")`). Write complex
  AC vectors through `vdb()`, `vm()`, `vp()`, `real()` or `imag()`.
- `value("f3db")` finds a value printed as `name = value` (by `meas`, or `print` of a `let` vector).
- `log()` is ngspice's output.

The run fails with `SimulationError::Ngspice` (the log and the kept run directory) if ngspice exits
with an error, prints a line starting with `Error`, or reports an analysis that stopped
(`tran simulation(s) aborted`, e.g. after `Timestep too small` in the middle of a transient
analysis, which ngspice reports without an `Error` line and with exit status 0). Otherwise the
directory is removed when the `Simulation` is dropped.

**Compatibility mode.** If models are marked as PSpice or LTspice, the deck needs ngspice's
`ngbehavior` mode (`SpiceNetlist::ngbehavior()`): `ps`, `lt` or `ltps` when the models are included,
with `a` appended (`psa`, ...) when one is written into the deck, since ngspice translates only
included files otherwise. `run()` writes `set ngbehavior=<mode>` to `.spiceinit` in the run
directory, which ngspice reads (`.options ngbehavior=` in the deck has no effect). Without a mode
it writes `unset ngbehavior`: ngspice reads only one `.spiceinit`, the one in its working
directory if there is one, so the user's `~/.spiceinit` does not affect the run. The deck notes it
after the title, `* requires: set ngbehavior=ps (.spiceinit)`, for running it by hand. Decks
without such models run in the default mode. See `doc/spice_part_macro.md` section 4 for what the
modes change.

`run()` runs `ngspice -b deck.cir` (`Ngspice::default()`, the program from `PATH`); another
program can be given with `Ngspice::new(program).run(&deck)`.

**Results without errors can still be wrong.** For a floating node or a node without a DC path to
ground, ngspice falls back to gmin and source stepping and then to a transient operating point, and
may report a plausible-looking result instead of failing. ERC (`doc/erc.md`) catches unconnected
pins but not a missing DC path; check results against what the circuit can do.

**Shared library.** With the `shared-ngspice` feature, `SharedNgspice::default().run(&deck)` runs
the same deck in the ngspice shared library (`libngspice.so.0`, `libngspice.0.dylib` on macOS and
`ngspice.dll` on Windows, loaded at run time; another file with `SharedNgspice::new(path)`) and
returns the same `Simulation`. It is the backend for co-simulation with Rust models; plain runs
should keep using the CLI:

- The library has global state, so it runs one deck at a time in the process (other threads wait),
  and a crash of ngspice takes the test process down. The CLI runs in parallel and isolated.
- The run directory holds `deck.cir`, which `ngspice -b deck.cir` runs as the CLI would, and
  `shared.cir`, the form the library runs: without `quit`, and with the relative output files of
  `wrdata`, `write` and `wrs2p` made absolute, since the library runs in the working directory of
  the process (`write` without a file writes `rawspice.raw` in the run directory, as the CLI does).
  Other commands writing files (`print ... > file`) need absolute paths, and `wrs2p` needs a file.
  The run directory must not contain whitespace or `"` (ngspice takes them literally).
- The compatibility mode is set by `set ngbehavior=<mode>` (or `unset ngbehavior`) before the deck
  is read. A deck without a control block is run with `run` after it is read, so the analyses of
  its dot directives (`.tran`, `.meas`) run as in the CLI.
- The library reads the user's `.spiceinit` when it is loaded: the one in the working directory of
  the process, or else `~/.spiceinit`. The CLI does not (see above), so settings there can make the
  two differ. ngspice cannot be told to skip it on Linux and macOS (`ngSpice_nospiceinit` only
  works in the Windows build).
- The library is loaded for each run and unloaded after it, so nothing a run sets (`set`,
  `option`, `define`, ...) carries over to the next run, also after an error ngspice cannot recover
  from (it reports `cannot recover and awaits to be reset`).
- The commands of the background thread (`bg_run`, `bg_halt`, ...) are not supported
  (`SimulationError::SharedLibrary`): the run would end, and the circuit be removed, while the
  analysis goes on.

`SharedNgspice::run_with` (and `SpiceDeck::run_with`) runs a deck with Rust models of devices:
see `doc/cosimulation.md`.

`Ngspice` and `SharedNgspice` implement the `Simulator` trait (`run(&deck)`), so a test can run on
either. The simulation tests of the library run on both when the feature is enabled.

The devcontainer provides `ngspice` and `libngspice0`; the simulation tests need them.

On Windows, `Ngspice::default()` runs `ngspice_con`, the console program of the Windows builds
(`ngspice` there is the GUI). The shared library of the official build is `ngspice.dll`; MSYS2's is
`libngspice-0.dll`, set with `SharedNgspice::new`. On macOS, Homebrew puts
`libngspice.0.dylib` in `/opt/homebrew/lib`, which the dynamic loader does not search by default:
give the path, or add the directory to `DYLD_FALLBACK_LIBRARY_PATH`. Homebrew's library also
lacks `spinit`, the script that loads the XSPICE code models (needed by `spice::ibis` and models
using `pwl`, `d_state`, ...): set `SPICE_LIB_DIR` to `$(brew --prefix ngspice)/share/ngspice`,
whose `spinit` loads them. MSYS2's `spinit` is not found either, and names the code models by MSYS2
paths; CI sets `SPICE_LIB_DIR` and rewrites the paths (`.github/workflows/ci.yml`). Paths are
written into decks with `/` on Windows, since ngspice reads `\` in commands as an escape. The output is
checked against KiCad's SPICE export as described in `doc/dev/verifying.md`.

## 6. Output

- `SpiceNetlist` has a title line, the compatibility-mode comment if needed (section 5),
  `.include` lines (absolute paths, sorted), inline `.model`/`.subckt` definitions (sorted by
  name), the element lines, and `.end`. A `SpiceDeck` adds its directives and the `.control` block
  before `.end`.
- Elements follow the component order of the netlist (subcircuit instance by instance, then by
  reference). KiCad uses the schematic order; ngspice does not care.
- Element names are the device letter, the reference and the suffix (`XU1A`). The letter is
  prepended only when the reference does not already start with it (`R1`, not `RR1`), as KiCad does.
